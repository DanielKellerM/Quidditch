# Documentation — the standard

Docs are a **reviewed dimension**, not an afterthought. A principal engineer's
repo has docs that are honest, navigable, and — above all — **rot-proof**. Review
docs with the same severity scale as code: a doc that restates a constant that
lives in a generated header is a TASTE finding; a runbook whose command no longer
exists is a BLOCKER (it actively misleads).

## Principles (enforce these)

1. **Measured > projected.** Every performance claim is sourced from real numbers
   (bracketed `mcycle`, a cycle table, a test result). Never "should be ~2× faster"
   — show the table. The existing `docs/host-device-split.md §2` is the model.
2. **Status + audience up front.** A design doc leads with **Status** (phase,
   what's done vs in-flight) and **Audience**. A mandatory **Risks / unknowns
   (honest)** section, not an optional one.
3. **Reference generated sources; never restate constants.** Do not write
   `L1 base 0x30000000` in prose — write "L1 base (cfg: `alias_region_base`)" and
   point at the generated `snitch_cluster_cfg.h`. Same for tile sizes, DIMs, tool
   versions (point at `pyproject.toml`/lockfile), ABI offsets (point at the
   header). If a value is hand-maintained, mark it **MANUAL** and name the owner.
4. **The ABI header is canonical.** Docs *reference* `cluster_command_stream.h`;
   they never duplicate the struct layout. One source of truth (see
   `abi-and-versioning`).
5. **Runbooks are instructions, not essays.** build-this → run-this → you-should-
   see-X. Every command runnable, every expected output machine-checkable.
   Separate "what's already verified" from "what this runbook adds."
6. **Subsystem READMEs own their scope** and link up to `architecture.md` for the
   big picture — no cross-subsystem prose duplication.
7. **Example code is load-bearing.** Before/after MLIR, hex dumps, exact build
   commands — the reader should see precisely what to type/expect.

## Rot patterns to flag on sight (found in the current docs/)

- **Hardcoded addresses in prose** (`0x30000000` restated instead of cfg-linked)
  — the moment the cfg changes, the doc lies. TASTE, or BLOCKER in a runbook.
- **Bare commit/branch references** (`commit 3d064f9`, `branch cheshire-...`) that
  stale when rewritten/deleted → link to a tag or describe the change instead.
- **External task IDs** (`task #19`) with no back-link and no status sync.
- **Assumed-stable source paths** with no "generated by / lives at" note — a
  refactor silently breaks the doc.
- **Magic problem dimensions** (`DIM 16` vs `64`) as prose numbers, not references
  to the build constant.

## Doc style — real examples from the tree

**File-banner doc comment** — problem statement, then the contract, then the
invariants (`runtime/host/transport/cluster_command_stream.h:1`):
```c
// Host<->Snitch-cluster job ABI for the Cheshire/Carfield host-device split.
// ... the host serializes a recorded command buffer into a flat command stream
// in shared memory ... rings a doorbell ... the cluster DM core parses and
// replays it ... then signals completion.
// This header is the contract between the two sides and is deliberately
// dependency-free (only <stdint.h>) so it compiles for both the rv64 host and
// the rv32 firmware. All multi-byte fields are little-endian ... Binding
// addresses are DEVICE-physical (the host translates host-VA -> device-PA).
```
No decoration; every line carries a contract or an invariant.

**Function doc** — one self-sufficient sentence, no `@param` noise
(`iree/.../hal/drivers/cuda/cuda_device.h:20`):
```c
// Creates a device that owns and manages its own CUcontext.
iree_status_t iree_hal_cuda_device_create(...);
```

**Design doc** — Status + Audience, then Why / measured Payoff / What / Risks /
Phasing, numbered and independently navigable (`docs/host-device-split.md:1`). The
payoff is a measured table ("~39.2k → ~4.2k, 9.3×"), not a projection, and §8 is
"Risks / unknowns (honest)".

**Runbook** — goal → gap → evidence → what-changes → command → expected output,
with a "What's already verified" table separating oracle from hypothesis
(`docs/multicluster-4x4-runbook.md:1`).

**xDSL docstring** — algorithm name + intent (honest: "Naive"), then a
before/after MLIR example that is load-bearing (`xdsl/.../stencil_bufferize.py:65`).

## The Nimbus doc set (target structure)

Rot-proof by construction: each references generated sources, leads with status,
and separates verified from planned.

| Path | Purpose | Must contain |
|---|---|---|
| `README.md` | Land here first: what/ready?/build/parts | tagline, **status block** (fork pins → link lockfile), quickstart (clone→toolchain→uv→cmake→ctest), dir tree w/ 1-line purposes, one host↔cluster diagram, links to the docs below |
| `docs/architecture.md` | The split model + measured payoff | measured before/after table (mcycle method), component-ownership table (stays-on-cluster / moves-to-host / new), transport diagram → links `abi.md`, phased roadmap w/ per-phase test criteria, honest Risks |
| `docs/abi.md` | Host↔firmware wire contract | shared-memory layout diagram, job-descriptor + record-type breakdown **linking `cluster_command_stream.h` (never duplicating it)**, publish/consume ordering, versioning/feature-flags, an explicit "generated vs MANUAL" section |
| `docs/bringup-runbook.md` | Validate each phase | per-phase: goal / prereqs (Phase N-1 ✓) / exact command / expected output signal / what it validates; a troubleshooting matrix at the end |
| `runtime/host/README.md` | Host IREE runtime + cluster HAL driver | dir layout (transport/hal-cluster/firmware/cheshire), integration points (plugin reg, allocator returns device-PA, completion semaphore), build cmds, common pitfalls |
| `runtime/firmware/README.md` | The thin cluster replay loop | what it reuses (dispatch.c fan-out, snRuntime), the ABI it parses, the two-path dispatch (LLVM workgroups vs Snitch-native), build/toolchain |
| `codegen/README.md` | MLIR → executable pipeline | stages (iree-compile → host vm-c + Snitch `.o`), lowering_config, build cmds, autotuner hook |
| `runtime/samples/README.md` | How to add a model/kernel | copy-a-sample steps, `CMakeLists.txt` + `main.c` templates, test wiring |
| `tools/autotune/README.md` | The tuning loop | L1/L2 architecture, the Phase-0 gates (throughput + is-there-a-win), search space, regression pin, DIM-scaling pitfall |

**Consistency rule:** every design doc follows the same skeleton — *Status ·
Audience · Why · Payoff (measured) · What · How · Risks · Phasing* — so a reader
can skip straight to a section and know it exists.
